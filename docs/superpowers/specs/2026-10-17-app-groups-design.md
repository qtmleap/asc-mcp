## Protocol boundary

The official ASC OpenAPI4.5.1 has no App Group resource. Use a separate Developer Portal client, not an invented public JWT endpoint and not a wider `Reviewer::fetch` origin allowlist. The fixed production origin is `https://developer.apple.com`; the fixed endpoint family is `/services-account/QH65B2/`. A test-only constructor may use loopback and is unavailable through CLI/environment/MCP arguments.

Use the primary fastlane Portal implementation as protocol evidence: `account/listTeams.action`, `account/ios/identifiers/listApplicationGroups.action`, `addApplicationGroup.action`, `assignApplicationGroupToAppId.action`, `listAppIds.action` and `getAppIdDetail.action`. These are form-encoded POST endpoints, including reads. Encode repeated association values as `applicationGroups[]`. Interpret operation semantics explicitly, not HTTP method alone. Use `reqwest::retry::never()` and `Policy::none()`: never follow redirects or automatically replay a request. Each request has a30-second timeout and an8MiB streaming response cap; each complete operation has a120-second deadline. Require successful HTTP status, `resultCode == 0` and the expected typed body. Unknown formats fail closed; HTTP200 alone is not success. No arbitrary paths or URLs are accepted.

The endpoints are undocumented, may change and are not certified by offline tests. Documentation and tool descriptions disclose this. Required Apple role is Account Holder or Admin; verified Team membership is not a promise of sufficient mutation permission.

## Tools and configuration

Tools are exposed only with explicit `ASC_DEVELOPER_APP_GROUPS_ENABLED=true`; malformed configuration stops startup with a redacted configuration error. Listing the ordinary catalogue without opt-in does not expose them. Add strict module-owned argument validation; generic protocol validation does not enforce every JSON Schema constraint. Developer-only discovery/dispatch and `validate` must work without a public API client or Reviewer, without exposing the unconfigured public catalogue. Preserve existing reviewer-only behavior, and update all Server struct-literal tests and the CLI's separate tools path.

- `get_developer_connection_status`: reports configuration and read-only Team access without account identifiers or secrets.
- `list_app_groups(team_id)`: returns complete bounded pages for the explicitly requested Team.
- `get_bundle_id_app_groups(team_id, bundle_id)`: resolves an exact iOS bundle identifier in that Team and returns its complete current group associations.
- `create_app_group(team_id, identifier, name, dry_run=true, operation_id?, confirmation_token?)`: dry-run produces a short-lived exact registration plan; execution requires the same arguments, operation ID and confirmation token.
- `associate_app_group(team_id, bundle_id, identifier, dry_run=true, operation_id?, confirmation_token?)`: plans or executes addition of one existing group, never removal.
- `get_app_group_write_status(operation_id)`: reports the private receipt and may perform only read-only reconciliation. It never resumes a write.

Every read and write verifies exact Developer Team membership through the Developer endpoint. Numeric ASC provider IDs are never interpreted as Team IDs. Team IDs are ten uppercase ASCII alphanumeric characters; resource IDs are validated independently. Explicit reverse-DNS identifiers are at most255 ASCII characters, with no wildcard; group identifiers start with `group.`. Names use the conservative1–100-character pattern `[A-Za-z0-9][A-Za-z0-9 _-]{0,99}`; unsupported input is rejected, never transliterated or silently rewritten. Unknown/extra arguments, wrong types, incomplete pages, ambiguous identities and inconsistent duplicate records are rejected. List calls use pageSize100 with at most100 pages; groups are additionally capped at1000 and App IDs at10000. Validate reported total/count metadata against unique records and reject changed totals, duplicates or any partial read rather than using partial state.

Association resolves the exact App ID and group inside the same Team and verifies their identities from detail/list responses. It does not assume an old App ID prefix equals Team ID. The App Groups capability must already be enabled; enabling capabilities is not a hidden second write. Missing or malformed association data is unknown, never an empty set. The reported `associatedApplicationGroupsCount` must equal the unique complete association count; inconsistent or unavailable completeness metadata prevents a write.

## Confirmation, persistence and unknown delivery

A dry-run returns the exact Team, identifiers, requested name or existing/proposed group sets, replacement-semantics warning, operation UUID, expiry and an opaque random256-bit confirmation token. Store its hash alongside the canonical plan digest, not a forgeable client-only digest. Plans bind operation type, complete request, resolved internal IDs, source generation and association baseline, and expire after15 minutes. Execution must match this server-stored plan exactly and consumes it once. Tokens are not authentication credentials and do not substitute for explicit human authorization: approval relies on the MCP host/client's tool-approval controls and the operator's decision. A bearer-authorized MCP caller can prepare and execute; the server does not independently attest a human click. No extra per-operation CLI approval is added.

The dedicated cross-process lock protects source/overlay reads, planning, conflict checks and receipt transitions, and stays held across the bounded network operation. Acquire it nonblocking; another caller receives `developer_busy`, not a hidden wait/retry. Persist a private `attempting` receipt atomically before dispatching a mutation, then send it at most once. If recording intent fails, do not send. State transitions are `prepared -> attempting -> verified | rejected | delivery_unknown`. After acquiring a free lock, any previously persisted `attempting` receipt is treated as unknown; no PID/boot assumption is required. Unresolved-intent blocking keys are registration `(team, identifier)` and association `(team, bundle_id)`, independent of operation UUID, requested name/group and authentication generation. Find conflicts by scanning a bounded, fully validated receipt store under this same lock, not by an independently updated index. Repeated execution, another operation ID, another requested group, re-login or restart cannot bypass that block. Verified/rejected operations are consumed but do not block a distinct newly confirmed operation. Do not log or persist raw responses, passwords, cookies or CSRF headers in plans/receipts.

Receipt schema1 contains only operation UUID/type, state, Team, target identifiers/internal IDs, requested name if any, source generation, confirmation-token hash, canonical-plan digest, creation/expiry times, baseline/expected group ID sets and a fixed-code observation. Limit each record to64KiB and the store to2048 records; capacity exhaustion stops new planning/writes. Expired prepared records and verified/rejected records older than30 days may be pruned under lock. Never prune attempting/unknown records. A mismatched readback is persisted as an unknown fixed-code observation, not merely printed.

Only an explicit, typed Apple rejection can be `rejected`. Transport errors, redirects,5xx, malformed responses, unexpected successful bodies, failed readback and failed final receipt persistence remain unknown. A read-only status check may report the desired state is now observed, but must not claim that an ambiguous request created it. Neither observed presence nor absence proves a timed-out request cannot apply later; reconciliation does not consume an unknown receipt or release its write block. This first version has no automated unknown-intent override. Operator guidance is to retain the receipt, inspect Portal state outside automation and resolve through support/future explicit recovery tooling; never advise deleting receipts or switching state roots to retry. No automatic rollback or compensating mutation is attempted.

Registration first checks for an existing exact identifier. An already-existing exact desired group is a no-op, not a new creation; conflicting identity/name does not overwrite it. Successful creation requires exact resource identity and a fresh complete readback.

Association uses `current union requested`, preserving every existing group. Re-read complete detail immediately before dispatch and reject a changed baseline; send no empty or partial array. Verify the complete expected set afterward and report any mismatch without retry. The private endpoint provides no atomic external CAS, so another Portal/Xcode writer can still race between check and write. Disclose this residual risk in the confirmation and docs; do not claim atomic additive behavior. Local concurrent operations remain serialized.
